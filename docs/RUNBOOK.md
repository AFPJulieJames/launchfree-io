# The Runway — New Listings Build Runbook (SOP)

House style: no em dashes anywhere. Preferred deploy tool: GitHub Desktop.

This is the standard operating procedure for taking approved submissions and publishing them as
live listing pages on LaunchFree.io, cleanly, every time. Follow it start to finish. It exists so
the rework we had to do once (wrong slugs, a duplicated `listings 2` folder, disconnected votes,
un-indexed pages, a blocked push) never happens again.

---

## 1. Source of truth and golden rules

1. **The connected repo is the only source of truth.** Work happens inside the `launchfree-io`
   repo folder, connected to the session. Not in a scratchpad, not in a zip, not in Airtable.
2. **Build directly in the repo. Never unzip a delivered folder into it.** The `listings 2`
   mess came from unzipping a `listings/` folder into a repo that already had `listings/`, which
   macOS renamed to `listings 2`. Deliverables are written straight into `listings/`, one file at
   a time. No archives are ever expanded inside the repo.
3. **`listings.json` is the catalog.** The homepage and browse page read it live at page load.
   Add every new launch here or it does not appear on the site.
4. **One slug, decided once, never changed.** The slug is the filename, the vote key, and the
   backlink. Renaming a live slug breaks all three. See section 3.
5. **Votes live in Supabase, not in files.** Every listing page and the grid read live counts.
   New records are created with `votes: 0`. Never hardcode vote numbers again.
6. **Only GitHub Desktop manages git. The assistant never runs git against the repo.** Claude
   reads and writes files only. Julie stages, commits, fetches, pulls, and pushes in GitHub
   Desktop. Two git processes on the same repo create the `.git/index.lock` that blocks commits,
   so the assistant stays out of git entirely (no `git status`, no `git commit`, nothing). See
   section 6.
7. **Nothing is "done" until it is verified live.** Verification uses the live site and the
   Supabase API through the browser, never `git`. See section 7.

## 2. What to update on every build (the four surfaces)

A page file alone is invisible. Every build touches these, together, in one commit:

| Surface | What to do | Auto or manual |
|---|---|---|
| `listings/<slug>.html` | Create the page from `template.html` + the vote script | Manual (generated) |
| `listings.json` | Add one record per launch (schema in section 4) | Manual (generated) |
| `sitemap.xml` | Add one `<url>` per new page before `</urlset>` | Manual (generated) |
| `llms.txt` | Add one line per new page under "Recent launches"; update the launch count | Manual (generated) |
| `index.html` / `browse.html` | Nothing. They fetch `listings.json` live and update themselves | Automatic |

If any of the four manual surfaces is skipped, the launch is half-published. The pre-flight
checklist in section 5 catches this.

---

## 3. The slug standard (the streamlined rule)

**Going forward, every slug is kebab-case, produced by one deterministic rule. No exceptions,
no judgment calls.**

The rule, in plain terms:
1. Lowercase the product name.
2. Strip accents (á becomes a, é becomes e).
3. Replace `&` with the word `and`.
4. Replace every run of non-alphanumeric characters (spaces, dots, slashes, punctuation) with a
   single hyphen.
5. Trim hyphens from the ends and collapse any doubles.

Examples:
- `VC Dekho` -> `vc-dekho`
- `Pocket Invoice` -> `pocket-invoice`
- `Dear Passengers Guide` -> `dear-passengers-guide`
- `agentskills.codes` -> `agentskills-codes`
- `frontend.watch` -> `frontend-watch`
- `Filings.ae` -> `filings-ae`
- `Hacé Cuentas` -> `hace-cuentas`
- `Screen Break` -> `screen-break`
- `RouteSheet` -> `routesheet` (one word, so no hyphen)
- `Nozzio` -> `nozzio`

Rules of the road:
- **Decide the slug once, at creation. Never rename a live page.** A live slug is load-bearing:
  it is the URL builders shared, the dofollow backlink Google indexed, and the key its votes are
  stored under in Supabase. Renaming orphans all three. If a slug is ever genuinely wrong, that is
  a redirect conversation, not a rename.
- **Collision check.** Before creating a page, confirm the slug is not already in `listings.json`
  or `listings/`. If it collides with a different product, append a short qualifier
  (for example `-app` or the platform) and keep it stable.
- **Existing pages keep their historical slugs.** About a quarter of the current catalog was
  generated with a concatenated style (`blurbackground`, `videoupscaler`). We do not touch those.
  The mix is cosmetic and every URL is permanent. Consistency starts with new pages, not by
  rewriting history and breaking links.

Why they looked inconsistent before: pages were generated by more than one method over time and
no single slug rule was enforced. This SOP is that rule.

## 4. Step by step

### Step 0 — Connect the repo
Connect the `launchfree-io` folder to the session so pages are written straight into it. All the
following steps read and write inside that folder.

### Step 1 — Reconcile against the catalog (prevents duplicates)
Load `listings.json` and the `listings/` filenames. For each approved product, compute its slug
(section 3) and check whether it already exists.
- Already present -> skip. It is already live. Do not rebuild or duplicate it.
- Not present -> it is genuinely new, queue it to build.
Collapse duplicate submissions of the same product to one. One builder submitting several distinct
products is fine; each is judged on its own.

### Step 2 — Live review each new URL (the approval standard)
For every new product, open the live site with `web_fetch` and confirm it is a real, working
product within standards: no dead or empty pages, no fraud or terms-of-service violations (OTP or
verification bypass, reselling other people's AI or software subscriptions, account trading), no
crypto tokens, no deceptive claims, nothing unsafe involving minors. Mark each Approve, Review, or
Reject with a one-line reason. Build pages only for confirmed Approves.

### Step 3 — Generate the pages
For each Approve, build `listings/<slug>.html` from `template.html`:
- Fill the `LISTING = { ... }` object with the product's data (name, tagline, url, description,
  category, stage, pricing, emoji = first letter, date, builder name and bio and story).
- Append the voting script block before `</body>`, tagged `data-lf-vote-backend="1"`, with
  `SLUG` set to this page's slug, and make sure the page has a button with `class="upvote-btn"`.
- The page must never be hand-written or pasted from elsewhere. Same template, same script, every
  time. That is what keeps the buttons alive and the design consistent.

### Step 4 — Update the three data surfaces
- `listings.json`: append one record per launch (append, do not rewrite the file):
  `{ "id": slug, "name", "tagline", "desc", "emoji", "logo": "", "cat": category, "url",
  "stage", "votes": 0, "featured": false, "slug": slug, "date": "YYYY-MM-DD", "mrr": "" }`
  Note `id` and `slug` are the same value. `votes` is always 0.
- `sitemap.xml`: insert one `<url>` block per page before `</urlset>`.
- `llms.txt`: insert one line per page at the top of "Recent launches"
  (`- [Name](https://launchfree.io/listings/<slug>.html): <tagline> (<Category>).`) and update the
  "currently N live launches" count.

### Step 5 — Pre-flight checklist (before any commit)
Run through section 5 below. Fix anything that fails before committing.

### Step 6 — Commit and push (GitHub Desktop)
See section 6.

### Step 7 — Verify live (after deploy)
See section 7.

## 5. Pre-flight checklist (must all pass before commit)

- [ ] Every new page exists at `listings/<slug>.html` with a kebab-case slug from the rule.
- [ ] Every new page contains `data-lf-vote-backend` and the `SLUG` inside it matches the filename.
- [ ] Every new page has a `class="upvote-btn"` button.
- [ ] `listings.json` is valid JSON, has one new record per launch, `id == slug`, `votes: 0`.
- [ ] No duplicate slugs in `listings.json`.
- [ ] `sitemap.xml` has one new `<url>` per page and still ends with `</urlset>`.
- [ ] `llms.txt` has one new line per page and the launch count is updated.
- [ ] No stray folders inside `listings/` (no `listings 2`, no nested `listings/`), and no leftover
      zip or duplicate files anywhere in the repo.
- [ ] The changed-files list is exactly what you expect: the new pages plus `listings.json`,
      `sitemap.xml`, `llms.txt`. Nothing else, no surprise renames.

## 6. Commit and push with GitHub Desktop (preferred)

1. Open GitHub Desktop with `launchfree-io` as the current repository.
2. In Changes, confirm the file list matches the pre-flight expectation (new pages +
   `listings.json`, `sitemap.xml`, `llms.txt`). If a `listings 2` or other stray folder appears,
   stop and remove it before committing.
3. Write a clear summary, for example `Add N new listings (voting + indexes)`, and click
   **Commit to main**.
4. Click **Fetch origin** first. If it says newer commits exist on the remote, click **Pull
   origin** to reconcile before pushing. Always fetch and pull before push. This avoids the
   "newer commits on remote" block.
5. Click **Push origin**. Wait for GitHub Pages to redeploy (about one to three minutes).

If a commit or push fails with "a lock file already exists": a stale `.git/index.lock` is
blocking it. Quit GitHub Desktop, then in Terminal run
`rm -f "/Users/jules/Documents/Claude/LaunchFree Hub/launchfree-io/.git/index.lock"`, reopen
GitHub Desktop, and commit or push again.

**Root cause and permanent prevention.** That lock kept reappearing because the assistant ran
`git` commands (like `git status`) on the same repo GitHub Desktop was using. Git created the lock
on the mounted folder and could not clean it up, so it went stale and blocked the next commit. The
rule that prevents it: the assistant never invokes `git` on the connected repo. It edits files with
the file tools and checks state by reading files or the live site, never with git. Git is GitHub
Desktop's job, exclusively. With only one tool touching the index, the lock does not recur.

Never expand a zip into the repo to "add" pages. Pages are written into `listings/` directly, so
there is never an archive to unpack and never a `listings 2` collision.

## 7. Post-deploy verification (definition of done)

After Pages redeploys, confirm on the live site:
- [ ] A new listing page loads and renders its content (for example
      `https://launchfree.io/listings/<slug>.html`).
- [ ] Its upvote button shows a number and reads from Supabase (0 for a brand new launch).
- [ ] The homepage launch count reflects the new total.
- [ ] The new launches appear in the homepage or browse grid.
- [ ] `https://launchfree.io/sitemap.xml` and `llms.txt` include the new slugs.
- [ ] No stray path is live (for example a `listings/listings 2/...` URL should return 404).

Only when these pass is the batch done.

## 8. Anti-patterns (these caused the rework, do not repeat)

- **Unzipping a delivered folder into the repo.** Created the duplicate `listings 2`. Build in the
  repo instead.
- **Ad-hoc slugging.** Produced wrong filenames that did not match the catalog. Use the one rule.
- **Renaming a live slug.** Breaks the backlink, the shared URL, and the vote row.
- **Treating `listings.json` vote numbers as real.** The homepage used to show hardcoded seed
  votes and ignored Supabase. Votes now come from Supabase live; new records are always `votes: 0`.
- **Publishing a page without adding it to `listings.json`, `sitemap.xml`, and `llms.txt`.** The
  page exists but nothing points to it.
- **Committing without checking the changed-files list.** A surprise in the diff is a signal to
  stop, not to push.
- **The assistant running `git` on the connected repo.** Leaves a stale `.git/index.lock` that
  blocks GitHub Desktop from committing. Only GitHub Desktop touches git; the assistant only reads
  and writes files.

## 9. Voting architecture (so it is never re-broken)

- Backend: Supabase project `launchfree-votes` (ref `klsfvbmqlmmsdnfvoiqw`). Table
  `public.launch_votes` (slug, votes, updated_at). Function `increment_vote(p_slug)` is the only
  write path. Publishable key is client-safe and lives in the pages and in the grid. The secret
  key never goes in the repo.
- Each listing page reads its own count on load and writes one vote on click, guarded per browser
  by `localStorage` key `lf_vote_<slug>`.
- The homepage and browse grid batch-read all counts from Supabase on load and display live
  numbers, and their upvote buttons write through the same `increment_vote` path with the same
  per-slug guard. Sorting by votes uses the live numbers.
- The table is sparse: a slug appears only after its first real vote. Empty is normal for a new
  launch, it is not a bug.
- For the newsletter, pick the weekly winner from the Supabase table (approved that week, sorted by
  votes), never from `listings.json`.

---

## 10. One-line summary

Build each page in the repo from the template with the vote script, give it one kebab-case slug for
life, add it to `listings.json`, `sitemap.xml`, and `llms.txt`, run the pre-flight checklist, then
commit, fetch, pull, and push in GitHub Desktop, and verify it live. No zips, no renames, no
hardcoded votes.
