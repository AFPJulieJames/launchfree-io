## 3. The operating procedure to engrain (review, build, vote, ship)

This is the part you should not have to repeat. It is the condensed version of BUILD_SPEC. When a
new chat has submissions to process, this is the loop. Section numbers point at the full rules in
`docs/BUILD_SPEC.md`.

### 3a. Review every submission before building anything (BUILD_SPEC section 5)

Open every submitted URL live and judge it. Record one line per submission: **Approve**, **Review**,
or **Reject**, with the reason.

- **Approve** when the URL loads, the product is real and usable, and the submission matches what is
  actually there. Only confirmed Approves get built.
- **Reject** for a dead or parked link, fraud or terms violations (OTP or verification bypass,
  reselling someone else's AI or software subscriptions, account trading), crypto tokens or coins or
  investment schemes, deceptive claims or fake testimonials or invented metrics, anything unsafe
  involving minors, or "not a product" (a blank template, a personal blog post, a bare affiliate
  landing page).
- **Review** (fixable, worth an email) when the URL is not live yet, the same builder submitted the
  same product twice, there is a trademark problem, or it needs one clarification. Send the review
  email and hold it. Do not build it.

Duplicate submissions of the same product collapse to one listing. One builder submitting several
genuinely different products is fine, and each is judged on its own. **Watch the dedup:** match on
the full URL path, not just the domain, so one builder's three different products on one domain are
not collapsed into one.

### 3b. Build the page — template only, server-rendered (BUILD_SPEC sections 1, 4, 6, 7)

1. Derive the slug from the product name, once: lowercase, strip accents, `&` becomes `and`, every
   run of non-alphanumeric characters becomes one hyphen, trim and collapse hyphens. Collision check
   against `listings.json` and `listings/` first. Never rename a live slug. Never correct a
   historical slug.
2. Copy `docs/LISTING_TEMPLATE_SSR.html` to `listings/<slug>.html` and replace every `{{PLACEHOLDER}}`.
   Never build from `template.html`, never by copying another listing.
3. Delete optional blocks you have no data for (no logo, no pricing, no Twitter, no story, no
   screenshots). Delete, do not fake with filler.
4. Copy rules: no em dashes anywhere. Use "builder" (primary), "founder", or "co-builder", never
   "maker". Sidebar heading is "Behind the Launch", share heading is "Get Your Launch Seen". Light
   editing of the builder's text is fine (typos, paragraph breaks, cut a hard sell); do not rewrite
   their voice or add claims they did not make. Never publish Builder Email, MRR, or How Did You Hear.
5. The seven things that must be in the static HTML: a real title `Name — Tagline | LaunchFree.io`
   (never "Loading"); a meta description; a self-canonical (never the homepage); Open Graph and
   Twitter tags; a real H1 plus full description and story text; two JSON-LD blocks
   (`SoftwareApplication` and `BreadcrumbList`); and the vote script (next section). Three related
   cards, all in the same category, all pointing at pages that already exist.

### 3c. The voting mechanism (BUILD_SPEC section 7, item 7)

Votes are real and live in Supabase, not in the repo. Every listing page must carry all three of
these or the vote button is dead and the validator fails:

1. The Supabase vote script, tagged `data-lf-vote-backend="1"`.
2. A `SLUG` constant inside that script set to this page's slug, matching the filename exactly.
3. A `<button class="upvote-btn">` on the page for the script to bind to.

In `listings.json`, `votes` is always `0`. The file value is ignored; the real count comes from
Supabase at page load. Never treat the JSON vote number as real, and never hand-edit it. A new
launch correctly shows 0 until people vote. The template already contains the correct vote script;
building from the template is what guarantees all three pieces are present, which is one more reason
never to build a page by hand.

### 3d. The six surfaces — every build touches all six, in one commit (BUILD_SPEC section 9)

A page file on its own is invisible. Update all six together:

1. `listings/<slug>.html` — the new page.
2. `listings.json` — append one record (`id` equals `slug`, `votes` 0, `mrr` empty, `featured`
   false). Append, do not rewrite the file.
3. `sitemap.xml` — one `<url>` block per new page, before `</urlset>`.
4. `llms.txt` — one line per new launch, and bump the "currently N live launches" count.
5. `directory.html` — regenerate so counts and ItemList JSON-LD refresh.
6. `categories/<category>.html` — add the launch to its category page and update that page's count.

The fast, reliable path for surfaces 4, 5 and 6: after you hand-write the page and append to
`listings.json` and `sitemap.xml`, run the generators. They are idempotent and never touch git:

```
python3 docs/regen_indexes.py --write     # category pages, directory.html, llms.txt, homepage count
python3 docs/validate_build.py            # machine pre-flight, must report 0 errors
```

Do not run `rebuild_listings.py --write` casually. It re-renders every listing page from the
template, so if any live pages have drifted it will rewrite all of them and blow up your diff. For a
one-off edit to a single existing page, edit that page surgically instead.

### 3e. Validate, then ship (BUILD_SPEC sections 10 to 12)

Run `python3 docs/validate_build.py`. It must report 0 errors before you commit. Then hand off to
GitHub Desktop (section 2 above) and confirm on the live site that View Source shows the real
content. Nothing is done until that passes.
